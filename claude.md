# Project Development Context

_Last reviewed: 2026-09-26_

## Project summary

This directory contains a client-side web application that converts an uploaded image into a Perler bead pattern. The user chooses a target physical width and bead size; the app calculates the required bead-grid dimensions, resizes the image, maps each visible pixel to the nearest color in a Perler palette, and displays an interactive pattern with bead codes and an inventory count.

`specs.md` holds the requirements (each with an ID, a version marker, and a verification Check) and the decision log. `plan-v1.md` breaks v1 into milestones M0–M10. **M0 is complete**: the app was moved from a single HTML file onto Vite + TypeScript with no behavior change, and the Mini bead pitch was corrected to 2.6 mm (spec Q1). **M1 — replacing the element-per-bead grid with canvas rendering (decision D1) — is complete** (2026-09-13): canvas rendering, zoom by redraw, drag-pan plus the screen → cell mapping, bead codes with contrast and an 18 px legibility threshold, and `devicePixelRatio` applied once at the context. Max zoom was raised late from 30 px to 46.875 px, which the container-sized canvas made free. **M10 — pattern orientation (gridlines and edge rulers, decision D16) — is complete** (2026-09-13): `src/lib/guides.ts` holds the guide geometry, `canvas-view.ts` draws gridlines as a dark/light double rule plus per-axis edge rulers whose labels thin as zoom drops, and one "Grid" checkbox toggles both by redrawing. **M2 — the quality core — is complete** (2026-09-21): OkLab matching, area averaging in linear light, greedy perceptual color reduction (D17), the SET-4 color limit, and a lineart classifier (D18), all behind the GEN-6 pipeline boundary with two one-identifier strategy switches. GEN-2, GEN-3, GEN-4, GEN-6, GEN-7 and SET-4 are ticked. **GEN-8 is deliberately unticked** — the R1–R6 review does not fully pass, and ticking it would make the gate decorative. Two items remain: dark regions blend less smoothly than before D18 (improved, not closed — the three constants in `DEFAULT_CONTRAST_TUNING` are a live tuning surface meant to be moved by eye), and facial features of drawn characters distort, which is spec Q10 and is not reachable from this pipeline at all since the bead grid is fixed before any of it runs. NFR-2 is measured and over (315 ms at the hard limit against ~150 ms), recorded for M9 per D8. **M5 — the correction editor — is complete** (2026-09-22): brush, eraser, flood fill, stroke-scoped undo/redo, a two-tier color picker, and a pan mode that never paints. EDIT-1 … EDIT-5, EDIT-7 and EDIT-8 are ticked; EDIT-6 stays retired. D19 (2026-09-21) is what widened it, moving undo and fill from v2 into v1 and reversing D7. Three things from it are worth carrying forward: `src/state/pattern-state.ts` is now the single owner of the live pattern and its tallies, so anything that needs either subscribes rather than holding a copy; **`Pattern` did not change**, so M6 exports and M7 serializes exactly what the editor mutates; and **Q10 is answered — no mirror or copy-region tool** (written up at Q10 in `specs.md`), which leaves Q10 open only as a generation question. **M3 — input handling and errors — is complete** (2026-09-22): input failures are classified from the file's own bytes *before* any decode (D20), because `img.onerror` carries no reason and every decode failure otherwise looks identical from the inside. IN-2, IN-3, IN-4 and IN-6 are ticked, and IN-1 followed at M4 with the preview its Check also wants. Q4 is resolved by measurement rather than assumption — Safari decodes HEIC, Chrome refuses it — so HEIC is attempted and named only if it fails. **M4 — crop — is complete** (2026-09-22): a DOM preview carrying a draggable, resizable crop rectangle, with the geometry in `src/lib/crop.ts` and the pointer wiring in `src/render/crop-view.ts`. The crop reaches the pipeline as nothing but a nine-argument `drawImage` inside `rasterize.ts` — `SourcePixels`, `Pattern` and the GEN-6 boundary are all unchanged, so **M6 and M7 inherit nothing from it**. It ticked six requirements rather than the two it was scoped for: **IN-1, IN-5, SET-3, and SET-1, SET-2, SET-5** — the last three because each had correct arithmetic since M0 and an unticked box purely because its Check wants a number *displayed before Generate is pressed*, which is SET-3's readout, and which is why that readout was built first and everything else measured against it. Three traps are worth knowing about: **`image.width` changed meaning** the moment the decoded element went on screen (it reports the *rendered* width once an element is in the document, so every size now comes from the crop rect or `naturalWidth`); **EXIF orientation was verified, not assumed** — `naturalWidth`, the `<img>` render and `drawImage` do agree in oriented space, checked against a real orientation-6 JPEG; and **a drag on a full-image crop had to mean *draw*, not *move***, since at the opening state every point is inside the rectangle and a move clamps to a guaranteed no-op. **D21 came out of M4**: a successful generate hides the crop preview for good on that image — cropping is one-shot, because re-cropping over an image no longer on screen is messy — while **target width, bead size and maximum colours stay live**, so a pattern can be regenerated at a different size without re-uploading. The crop rectangle is kept, so a regenerate reuses the same framing; only a new upload reopens cropping, and it discards the old pattern. A rejected upload changes nothing but the status line, which revises M3 — its reason for clearing the loaded image was that without a preview you could not tell which image was loaded, and IN-5 removed that ambiguity. **D21 first froze every input and was narrowed the same day**; read it before re-widening it, and note what the narrowing leaves open: a second Generate still replaces the `Pattern` M5 mutates in place, destroying hand edits silently, recorded beside PAL-7 for M9. **M6 — PNG export — is complete** (2026-09-24), and it closed the critical path. It ticked OUT-1, OUT-2, OUT-3, and GEN-5, whose Check needed a PNG to exist. **D22** governs it: the export carries gridlines, a frame, and row/column numbers in a margin *outside* the cells; it is a **screen reference, not a print artifact** (codes readable when zoomed in on a screen); and it ignores the view's zoom, dpr and checkboxes, which is why two exports of one pattern are byte-identical (OUT-3). **"Fixed cell size" means fixed per pattern**: an oversized canvas encodes to nothing rather than throwing, so one budget, `EXPORT_MAX_PIXELS` (4096², the reported iOS cap), is respected *before* the draw, and the cell steps down from 32 px to an 18 px floor to fit. The hard limit exports at 18 px. That budget is **measured in headless Chrome only**; desktop Safari and a phone are recorded for M9 beside NFR-5. Printing large patterns (splitting into page-sized files) is deferred with OUT-6. **M7 — autosave — is complete** (2026-09-24): SAVE-1 and SAVE-2 are ticked, under **D23**. The save holds the pattern, the settings that *produced* it (captured at Generate, not the live inputs), **and the source image with its crop**, so a restored pattern can be regenerated at a new size without re-uploading. **Undo history is deliberately not saved** (D19; D23 records why restoring it would risk corrupting the pattern). Saving the image is what moved storage to **IndexedDB**: as base64, one phone photo overflows `localStorage`. The save mirrors the screen: it exists only while a pattern does, and a new upload empties it. Restore waits for the palette load to settle, because the editor resolves colors through the palette. An image that cannot be restored never costs the pattern. Safari's seven-day eviction is accepted, since the goal is surviving an accidental refresh, not archiving. Safari and a phone are unmeasured, recorded for M9 beside M6's canvas budget. **M8 — interface floor plus a styling pass — is complete** (2026-09-26). ## Commands

Requires Node >= 22. `npm install` first.

- `npm run dev` — Vite dev server with reload-on-save
- `npm run build` — static production build into `dist/`
- `npm run preview` — serve the built output
- `npm test` — Vitest, browser-free (`npm run test:watch` to iterate)
- `npm run typecheck` — `tsc --noEmit`; Vite strips types without checking them, so this is the only thing that enforces them
- `npm run check` — typecheck + tests, the full gate
- `npm run ui:audit` — the mechanical UI Checks (UI-1, UI-4, UI-5, UI-6) in every screen state at 1280 and 390 px, against a **running** app (`npm run dev` first; `APP=` to point elsewhere). Exits non-zero on a failure. `ui:focus`, `ui:file-picker` and `ui:fonts` are the companions; see `scripts/ui-check/` below

### How to run it

Use `npm run dev`. HTTP alone is **not** enough — a plain static file server (`python3 -m http.server`, `npx serve`) on the project root cannot run this app:

- `src/main.ts` is TypeScript. No browser executes TypeScript; Vite has to strip the types first. A file server just hands the file over, and Python compounds it by guessing MIME from the extension — `.ts` collides with MPEG transport stream, so it arrives as `video/mp2t` and the browser's strict module MIME check refuses it outright.
- `colors_221.json` lives in `public/`, which Vite serves at the URL root. A plain server doesn't know that convention, so the palette 404s.

To serve the app from your own static server, build first and serve the **output**, never the source: `npm run build && python3 -m http.server 8000 --directory dist`. `dist/` is compiled plain JS with the palette copied alongside, so a dumb file server is enough — at the cost of re-running the build after every edit.

Opening `index.html` as a `file://` URL fails too: browsers block `type="module"` scripts there regardless of build state.

In all three failure cases the module never executes, so `main.ts`'s own error handling cannot report it. The classic (non-module) boot guard inlined at the bottom of `index.html` exists for exactly that blind spot — it detects `file://`, script MIME rejection, and a startup throw, then writes an actionable message into the status line and leaves Generate disabled (PAL-3). Keep it inline and non-module; as a module or an external file it would fail in the very cases it reports. `src/main.ts` sets `window.__perlerBooted` at the end of its startup wiring to stand the guard down.

## Layout

- `index.html` — markup, plus the inline classic-script boot guard described above; loads `src/main.ts` as a module. The file input's `accept` list names the five formats **and `.heic`/`.heif` deliberately**: `image/*` hides HEIC in some pickers, and a file the user cannot select is a file we cannot explain (IN-4). It is only a hint either way — "All files" always defeats it — which is why the byte-level checks are the real gate. Since M8 that input is **visually hidden (`.sr-only`), not removed**: it is still what Tab lands on, what Enter/Space opens and what `main.ts` listens to. The visible "Choose image" is a second, aria-hidden `<label>` for it, and `#fileName` beside it names the loaded image (the input's `aria-describedby`). It also holds **eight icon buttons as inline `<svg class="icon">`** — M5's six editor tools, plus M8's two zoom buttons, which use the same `tool-button` class and swap rules — deliberately placeholders, in the 24 px stroke style Lucide/Feather/Heroicons-outline share. Swapping one is a paste: keep `class="icon"` and `aria-hidden="true"`, and leave the button's `aria-label` alone, because with the text labels gone that is the button's only accessible name. Icons draw in `currentColor`, which is why the pressed and disabled states need no second artwork. M4 added the crop preview, whose **two overlay layers are load-bearing and must not be merged**: `.crop-shade` carries the 9999 px `box-shadow` that dims everything outside the crop and lives inside a `.crop-clip` layer, because unclipped that shadow covers the whole page; `.crop-rect` carries the border and the four handles and must *not* be clipped, or a crop at the image edge loses the outer half of its handles. Both are positioned to the same rectangle. The `<img>` is inserted by `crop-view.ts` rather than written here, and the handles are plain divs — there is no keyboard crop in v1, and focusable no-op controls would leave M8 a UI-4 problem that looks like a bug. Every overlay layer is `pointer-events: none`, so gestures land on `.preview-frame` and `hitTestCrop` is the only thing deciding what was grabbed. M6's `#exportControls` (the Download PNG button) sits **below the canvas**, between `#outputContainer` and the bead list. It was moved there from beside `#stats` because the space above the canvas already holds the stats line, the zoom row and the editor bar. It is shown only while a pattern exists; M8 kept it there, as an outlined secondary button.
- `public/colors_221.json` — the default 221-color palette (`name`, `hex`, `rgb`), fetched at startup. It lives in `public/` because that is the only directory `vite build` copies into `dist/`; moving it back to the project root would work in `npm run dev` and 404 in the build.
- `src/main.ts` — startup wiring: DOM references, palette load, and the upload/generate listeners, plus the stats line as a `pattern-state` subscriber, and M6's export button: a subscriber that shows it while a pattern exists, and a click handler that reads `getPatternState()` at click time, which is all OUT-2 needs. The view, inventory, and editor modules attach their own. M4 added two things here. **`refreshDimensions` is SET-3**: the grid the current crop and settings *would* produce, in its own `#dimensions` element and never in `#stats` — that line describes the pattern that exists, this one the pattern that would. Its total is **beads, not cells** (D24): transparent cells are not billed, so it rasterizes exactly as a generate would and counts with `countBeads`, which must equal the generated `beadCount` exactly, not approximately. Once a pattern exists it is **hidden while the target width and bead size match the settings that produced it**, derived from `pattern-state.ts`, not a flag. Refreshes are batched to one per frame. It shows SET-5's message by catching the same throw `calculateDimensions` already raised. M7 added `restoreSavedSession`, which runs once the palette load settles. It claims an `uploadToken`, so an upload made mid-restore wins. It **decodes the saved image before installing the pattern**, because installing the pattern fires the autosave's `'set'`, which rewrites the slot from whatever image is loaded at that moment. `uploadedFile` is kept beside `uploadedImage` for the save. M8 added `showLoadedFileName`, called only at the two places an image becomes loaded (a successful upload and a restore), never on a pick. **`syncControls` is the one place that decides whether Generate is enabled** (palette readiness and whether an image is loaded); before it, `generateBtn.disabled` was assigned from three places that each knew part of the story. Anything that changes those inputs calls it rather than touching `.disabled` directly.
- `src/lib/pattern-utils.ts` — dependency-free palette normalization/validation, dimension calculation, RGB matching, inventory tallying. `findClosestColor` and `colorDistanceSquared` are **not** dead code after M2: they are GEN-6's required second algorithm, wrapped by `rgbMatcher`. Covered by `pattern-utils.test.ts`.
- `src/lib/oklab.ts` — OkLab conversion and distance, plus the 256-entry sRGB→linear table every pixel goes through. A neutral gray's `L` is exactly `cbrt(linear)`, which is both the test oracle and the reason gate thresholds compare cube roots. Covered by `oklab.test.ts`.
- `src/pipeline/generate.ts` — **the GEN-6 boundary**: pixels in, `Pattern` out, no DOM, so it stays testable in Node. Sequence is downsample → match → tally → reduce → remap → rebuild tallies. It does not branch on either strategy switch. `countBeads` is SET-3's pre-generate count (D24), and its result must equal `generatePattern`'s `beadCount`. Covered by `generate.test.ts`.
- `src/pipeline/color-match.ts` — GEN-2 as a factory, so the palette's OkLab values are computed once per generate rather than once per cell. **`ACTIVE_MATCHER` is one of GEN-6's two switches**; flip it to `rgbMatcher` for pre-M2 behavior. Covered by `color-match.test.ts`.
- `src/pipeline/downscale.ts` — GEN-4 and D18. `boxAverage` is the exact fractional-coverage box filter in linear light, alpha-weighted; `contrastPreserving` adds the lineart classifier. `cellCoverage` is the alpha half alone, for `countBeads`, and **repeats `downsample`'s coverage math line for line**: change one and you must change the other. **`ACTIVE_DOWNSAMPLER` is GEN-6's other switch** — flipping it to `boxAverage` is also the standing diagnostic, and is what localized the D18 color-speck bug. The three constants in `DEFAULT_CONTRAST_TUNING` are a live tuning surface, not settled values; GEN-8 is unticked because of them. Covered by `downscale.test.ts`.
- `src/pipeline/reduce.ts` — GEN-3 and D17: Phase A collapses near-duplicates below `MERGE_FLOOR`, Phase B enforces the SET-4 limit, both by `count × ΔE to nearest survivor`. Merges are path-compressed and every argmin tie-breaks on ascending palette index (GEN-7). Operates on palette indices only — it never sees cell positions, so it cannot cause or cure a localized defect. Covered by `reduce.test.ts`.
- `src/state/pattern-state.ts` — **the single owner of the live pattern, its tallies, and — since M7 — the settings that generated it** (M5). The stats line in `main.ts`, `render/inventory.ts` and `render/editor.ts` all subscribe through `onPatternChange` rather than holding their own copy, which is what keeps EDIT-4 true; before M5 those three each kept their own and had to be updated in lockstep. The `Pattern` object is mutated in place and never replaced by an edit. `patternEdited()` re-tallies from the pattern rather than trusting the stroke's incremental arithmetic — 0.5 ms at the hard limit, and it removes tally drift as a class. The settings live here rather than in the autosave, because the inputs stay editable after a generate (D21), so they cannot be read back as the pattern's settings.
- `src/lib/pattern-save.ts` — M7's stored format (D23), pure and DOM-free: two versioned records, **pattern** (a color table of full records plus an `Int16Array` of indices, `-1` for empty) and **image** (the uploaded `File` as a `Blob`, its name and type, and the crop). They are two records because the pattern is rewritten every stroke and the image never is. A per-generate `generation` id ties them together, and a pair that disagrees is a torn save: the image is dropped, never paired with the wrong pattern. Colors are stored as full records rather than looked up in the palette, so restore does not depend on the palette fetch. **The decoders never throw**, the same stance `image-file.ts` takes toward input it did not write. Covered by `pattern-save.test.ts`.
- `src/state/save-store.ts` — the IndexedDB slot: one database, one store, two keys, and a generate's two-key write done in one transaction. No dependency, and no decisions. It is browser glue and is verified in the browser, not mocked in Node.
- `src/state/autosave.ts` — one `pattern-state` subscriber plus the startup loader. `'set'` writes both records, `'edited'` (stroke boundaries, undo, redo) writes the pattern only, and `'cleared'` deletes both. Writes are serialized, and queued edits coalesce. **Only failed pattern writes are reported**, once until one succeeds. A failed delete is not reported: every upload clears the slot, and with storage blocked that delete fails, which used to put an autosave error over "Image ready".
- `src/lib/pattern-edit.ts` — the edit primitive: a `CellEdit` is `{index, prev, next}`, and **one `applyEdits` serves paint, undo and redo**, which is why EDIT-4 holds by construction. Also the stroke recorder, which keeps one record per cell holding the color that cell had when the stroke *started*. Covered by `pattern-edit.test.ts`.
- `src/lib/edit-history.ts` — the undo/redo stack (EDIT-7). Two things are load-bearing: pushing while the cursor is behind the end truncates the tail first, and the stack is bounded by **total recorded cells, not stroke count** — a fill at NFR-3's limit is one stroke of 50,000 records. `DEFAULT_CELL_BUDGET` is a judgment constant like `MERGE_FLOOR`, so the tests assert eviction behavior and never the number. Covered by `edit-history.test.ts`.
- `src/lib/cell-path.ts` — Bresenham between two cells. EDIT-1's named watch-for: pointermove reports samples, not a path, so a fast drag is dotted unless consecutive samples are joined. Covered by `cell-path.test.ts`.
- `src/lib/flood-fill.ts` — EDIT-8's region search. Iterative (a 50,000-cell region would overflow the call stack), matched on `color?.name ?? null` so `null` matches `null` and a deserialized pattern still fills, and **exact-match only — D19 refuses a tolerance**; a speckled background is an R2/GEN-3 defect. Covered by `flood-fill.test.ts`.
- `src/lib/palette-query.ts` — the color picker's ranking (EDIT-3 tier 2): text filter plus ~12 nearest by OkLab ΔE, over the same table `color-match.ts` builds for the matcher, so "close" means the same thing in the picker as in the generator. Covered by `palette-query.test.ts`.
- `src/render/editor.ts` — the editor's pointer wiring, tool state, and picker DOM. Holds no deterministic logic: it decides which pure function a gesture means and nothing else. The eyedropper (alt-click) is live in every tool and is the one canvas gesture that records no edit.
- `src/types.ts` — `PaletteColor`, `Palette`, `Pattern`, `PatternDimensions`, `ColorTally`, `SourcePixels`. `Pattern` is the durable contract: M1 renders it, M5 edits it, M6 exports it, M7 serializes it. **M5 did not change it**, deliberately.
- `src/rasterize.ts` — hidden canvas: image → `SourcePixels`. DOM decode only; all the math lives behind the pipeline boundary. Returns an *intermediate-resolution* buffer, not grid-sized: the source capped so neither side exceeds `SUPERSAMPLE (8) ×` the grid side and the total stays under ~4M pixels. Only that capping draw uses browser smoothing. `SUPERSAMPLE` 8 → 4 is the cheapest lever against NFR-2, which is currently over. **M4's crop is applied here and nowhere else**, as the source rectangle of a nine-argument `drawImage`; the pipeline never learns it exists. **Never read `image.width` in this file.** Since M4 the decoded element is also the on-screen preview, and `HTMLImageElement.width` reports the element's *rendered* width once it is in the document — it silently stopped meaning the intrinsic size. Every measurement comes from the crop rectangle, or from `naturalWidth` if it must come from the element.
- `src/lib/image-file.ts` — M3's input gate (D20): magic-byte sniffing, header dimension parsing for PNG/JPEG/GIF/WebP/BMP, and end-marker truncation detection, over two byte windows (first 64 KB, last 64 bytes). **Every parser returns `null` rather than throwing or guessing** — an unread header costs one extra decode, a false rejection costs a file that would have worked, and that asymmetry sets the tolerance of every check in the file. It also owns every user-facing input message, so they stay in one place and a test can assert they are pairwise distinct (IN-2). Two things not to undo: **HEIC/AVIF/TIFF are accepted for a decode attempt, never refused** (Safari reads HEIC, Chrome does not — Q4), and **the JPEG frame-header walk must never throw or loop**, only return `null`. Covered by `image-file.test.ts`.
- `src/palette.ts`, `src/upload.ts`, `src/status.ts`, `src/dom.ts`, `src/contrast.ts` — palette loading, file decoding, status messages, `requireElement`, and text-contrast choice. `upload.ts` is M3's browser half and holds no decisions: it slices two byte windows, asks `image-file.ts`, then decodes through an **object URL, not a data URL** (which base64-encodes the whole file and holds it live for the decode), and re-checks `naturalWidth`/`naturalHeight` as the backstop for headers the parser declined to read. It throws `UploadError`, which carries a machine-readable `reason` so callers need not match on strings.
- `src/lib/guides.ts` — pure geometry for the pattern-view guides (VIEW-6, VIEW-7): the gridline interval and its visibility threshold, which boundaries fall inside a visible range, the adaptive ruler-label step, and the per-axis test for whether a ruler is warranted. DOM-free; M6's PNG export is its second consumer (`gridlineIndices` over the full range gives the export's gridlines and label positions). Covered by `guides.test.ts`.
- `src/lib/viewport.ts` — pure viewport math for the canvas view: zoom limits, the centre-fixed scroll offset on zoom, the visible cell range, the code-legibility threshold (`shouldDrawCodes`), and the screen-point → cell mapping M5 will consume. DOM-free, so it tests in Node. Covered by `viewport.test.ts`.
- `src/render/canvas-view.ts` — the canvas pattern view (D1), which replaced the M0-only `dom-grid.ts`. **`clearPattern` is the inverse of `renderPattern` and has to stay one**: `renderPattern` shows the zoom row and nothing else hides it, so clearing must hide it and put the `#placeholderText` element back, or a cleared pattern leaves an orphaned row of controls over an empty dashed box. It re-inserts that element rather than re-creating it, because the markup lives in `index.html` and its styling in `styles.css`. Codes and rulers are drawn in the page's body face, read once from `--font-body` (`viewFont()`), and the view redraws on `document.fonts` `loadingdone`, because a canvas does not repaint when a web font arrives and an autosave restore can draw before it has. The export deliberately does not share this. M5 added four small seams and changed nothing else: `cellAtPoint`, `isPatternCanvas`, `redrawPattern`, and `setPointerMode`. The last one is the subtle one — a paint tool has to gate `beginPan` **and** put `touch-action: none` on the canvas, because the canvas sits in a native scroll container that would otherwise scroll a touch-drag instead of painting; both live on the `.painting` class so pan mode gets native touch scrolling back. Draws the visible cell range with zoom, drag-pan, bead codes (skipped below the legibility threshold), and the gridlines and edge rulers from `src/lib/guides.ts`. Rulers need no positioning of their own — the canvas is already pinned to the visible corner, so its first pixels are always on screen. The canvas is sized to the *container*, never the pattern: `#grid-wrapper` is an empty spacer sized to the pattern that drives the native scrollbars, and the canvas is a `position: sticky` overlay pinned to the visible corner. Every length here is a CSS pixel; `devicePixelRatio` is confined to `layout()`, which sizes the backing store and applies the density once via `ctx.setTransform` — so the draw loop reads the CSS sizes off the view state, never `canvas.width`/`.height`.
- `src/lib/export-layout.ts` — M6's export geometry, pure and DOM-free: cell size, margins, code font, interior gridlines, edge-number positions, the file name, and every refusal message. **Its signature is OUT-3's guarantee**: a layout is a function of the pattern's width and height plus two text measurements the renderer supplies, and nothing else. There is no parameter a zoom or a dpr could arrive through. Cell sizes are integers, so cell edges land on pixels without rounding (GEN-5). `EXPORT_MAX_PIXELS`, the 7 px code-glyph floor behind `MIN_EXPORT_CELL_PX`, and `EXPORT_LABEL_FONT_PX` are judgment constants like `MERGE_FLOOR`: tests assert behavior, never the numbers. Covered by `export-layout.test.ts`.
- `src/render/export-png.ts` — the export's browser half, holding no decisions: measure two pieces of text, ask the layout, draw onto a **detached** canvas (never in the document, never dpr-scaled, no transform), encode, and download through an object URL. Two things not to undo: a `null` blob from `toBlob` is an error with its own reason, never "nothing to do", because it is how an oversized canvas fails; and the canvas is shrunk to 0 × 0 afterwards, since iOS holds canvas memory until the element is collected. It reads none of the view's checkboxes: codes and gridlines are always drawn (D22). It throws `ExportError`, which carries a `reason` like `UploadError` does.
- `src/render/guide-style.ts` — the gridline rule and ruler-text colours, shared by `canvas-view.ts` and the export so a line reads the same in both. It is its own module because `canvas-view.ts` looks up DOM elements at load time, and the export must not depend on that.
- `src/render/inventory.ts` — the bead-count list (OUT-4), and **tier 1 of M5's color picker**: the rows are real buttons, and clicking one makes that color active. Reusing this list rather than building a second swatch-and-code list is why picking an in-pattern color costs the shopping list nothing. It reads `pattern-state.ts` rather than being handed counts.
- `src/lib/crop.ts` — M4's crop geometry, pure and DOM-free: clamping, translate-only moving, corner resizing, the two-point new box, and the hit test. **Everything is in integer source pixels** — the decoded image's own space, which is what `drawImage` consumes and what `calculateDimensions` needs, so a coordinate is converted exactly once at the gesture boundary. Normalized fractions would be rounded twice, and those two roundings are what "the pattern matches the cropped region" is checking. **`hitTestCrop` takes its slop in source pixels**, converted by the view from UI-6's 44 px screen target — a screen constant baked in here would be right at exactly one preview scale. `MIN_CROP_PX` is a judgment constant like `MERGE_FLOOR`: tests assert the floor holds, never the number. Covered by `crop.test.ts`.
- `src/render/crop-view.ts` — the preview's pointer wiring and overlay positioning, holding no geometry of its own. M7's `restoreCropPreview(image, crop)` puts back a saved rectangle, clamped through `crop.ts` rather than trusted, where `showCropPreview` resets to the full image. Measures the display scale from the frame's box (the frame shrink-wraps the image, so one rectangle serves both the scale and the coordinate origin) and recomputes it on resize, since the 640 px media query changes the preview's width. Two behaviors not to undo: **a drag on a full-image crop draws a new box rather than moving** — at the opening state every point is inside the rectangle, and a move clamps to a guaranteed no-op, so the first thing anyone tries would otherwise do nothing; and `img.draggable = false` plus `touch-action: none`, which are the mouse and touch halves of the same problem — a native image drag on one, a page scroll on the other.
- `src/styles.css` — all styling. Since M8 it is four-space indented and **every padding, margin, gap, radius and font size reads from `:root` scales** (UI-3). The only literals are zero, `auto`, or commented exceptions. Colour tokens exist for every interface colour; the crop overlay and the empty-swatch checkerboard keep literals as artwork. **A change of look is an edit to `:root` values, not to rules**, which was the point of doing UI-3 before D25's pass.
  Four things not to undo:
  - **one `:focus-visible` rule** draws every focus ring as an *offset* outline, and selection is an *inset* edge, so the two differ in shape (UI-4);
  - the scroll lists (`.bead-list`, `.picker-results`) carry both **padding and `scroll-padding`**, since padding alone still clips a ring when focus scrolls a row flush;
  - the tool-button rules are scoped `:is(.editor-controls, .zoom-controls)`, keeping the two-class specificity that beats the 640 px query's full-width `button`;
  - `--text-title` is a px value (56 / 37.333 px) because Jersey 10 is crisp only at multiples of its 18.67 px grid, while the rest of the type scale is rem.
  The `@font-face` rules load self-hosted Latin-subset `woff2` from `src/assets/fonts/` (Jersey 10 and Space Grotesk, each beside its OFL license). They are imported through Vite, so the build hashes them and a bad path fails the build.
- `scripts/ui-check/` — M8's measurement harness, kept for M9: headless Chrome over the DevTools protocol, using nothing but Node 22's built-in `WebSocket`. `cdp.mjs` is the shared driver. `audit.mjs` measures overflow, select truncation, 44 px targets, WCAG contrast (placeholders included) and the focus ring on every Tab stop, in six screen states at both widths. `focus-shots.mjs` screenshots each control focused. `file-picker.mjs` checks the upload control's behaviour. `fonts.mjs` reports which face Chrome actually painted and captures the canvas codes after a generate and after a restore. Output goes to the git-ignored `scripts/ui-check/out/`.
  Three traps the harness already handles, and a new script must too:
  - Chrome's full-page capture does not paint a nested scroll container outside the viewport (use `captureElement`);
  - after `blur()`, Tab resumes from the last focused element rather than the top (use `focusFromTop`);
  - a CDP key event without `text` does not activate the focused control.
  Two things it cannot judge, which the screenshots are for: text hidden by `text-overflow`, and its select-truncation guess, which over-reports on auto-width selects and is printed as "verify". Browser-free tests stay in `src/`; this is deliberately not part of `npm run check`, because it needs a running server and a Chrome install. `CHROME=` overrides the macOS path.
- `colors.json` — a 291-record palette with `name` and `hex` only. Not loaded by the app and it would fail PAL-4 validation as-is; it is an input to `helper.py`, kept for PAL-6.
- `helper.py` — adds RGB tuples to a hex-only palette JSON.
- `pixi.toml` — conda workspace for the Python side only. npm owns the web app; don't try to make pixi manage Node.

## Conventions

- Four-space indentation; no linter or formatter is configured.
- Deterministic logic goes in `src/lib/` or `src/pipeline/` and gets a test (NFR-4). Anything touching the DOM, canvas, or `FileReader` stays out of those directories so the tests keep running without a browser.
- Look up elements through `requireElement` from `src/dom.ts` rather than raw `getElementById`.
